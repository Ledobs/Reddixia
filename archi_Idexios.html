Architecture Globale

Vue logique du toolbox agentique Reddixia orchestré par Idexios. Organisation par étapes : requête, analyse, rubriques, sources, agents, traitement et sorties.

Description de l'architecture

Le diagramme présente une orchestration par étapes. L'utilisateur formule une requête; Idexios agit comme hub central pour qualifier l'intention, résoudre le contexte (périmètre et période), sélectionner une rubrique, puis router vers le Domain Pack requis. Les Domain Packs utilisent les sources nécessaires pour produire des sorties standardisées.

  • Routage par rubriques : Idexios qualifie l'intention (Portefeuille, Conseils, Scenarios, Livrables, Gouvernance) et sélectionne le Domain Pack utile. En fonction du domaine, d'autres rubriques ou sources complémentaires peuvent être exploitées.
  • Sources par défaut : Dataverse TPG (tpg_*) et SharePoint (Idexios-Prime) sont les sources par défaut. Il est possible d'arrimer des sources de systèmes de suivi financier lorsque l'agentique soutenant la reddition de compte est utilisée. Par exemple, dans un contexte TI, Système financier (source personnalisée) peut être connecté afin de suivre la facturation et concilier les données.
  • Traitement : les agents spécialisés appliquent des règles de calcul, de détection d'écarts, de synthèse et de génération d'artefacts, avec traçabilité vers les enregistrements et procédures.
  • Sorties (3 formats) :
    1. Conversation : réponse structurée et contextualisée dans Copilot Studio.
    2. Power Pages : objets de rapport et Adaptive Cards affichables (drill-down et navigation).
    3. Process : écriture dans des tables et/ou formulaires lorsque la demande déclenche un workflow.

Flux d'Orchestration des Rubriques

Comment Idexios traite les requêtes utilisateur via ses 9 rubriques personnalisées, routant intelligemment vers les analyses appropriées.

Flux des Rubriques — Spécification des sorties (Adaptive Cards & Rapports)

Documente ici le contrat d’orchestration Idexios pour que l’équipe d’implémentation livre des Adaptive Cards et des rapports reproductibles, mesurables (PMI/EVM), et auditables (gouvernance/FinOps). Je m’appuie sur Dataverse (tpg_*) et Idexios-Prime (SharePoint) comme sources de vérité.
Principe non négociable : si une métrique n’est pas disponible (champ non exposé / pas de droits / pas de période), Idexios doit le signaler explicitement et demander les filtres manquants.

Schéma — Orchestration Rubriques ↔ Agents

Représentation synthétique des allées-retours entre l’orchestrateur Idexios, les rubriques (qualification d’intention) et les agents spécialisés (Domain Packs). Le schéma illustre la boucle de clarification, le routage, la récupération des données, puis l’assemblage des sorties.

Description des interactions

  • Qualification : Idexios interprète la demande et sélectionne une rubrique (Portefeuille, Conseils, Scénarios, Livrables, Gouvernance).
  • Clarification : si le contexte est incomplet (projet/programme/portefeuille, période, filtres), Idexios déclenche une boucle de questions/réponses avant calcul.
  • Routage : la rubrique active détermine le Domain Pack utile; l’orchestrateur appelle ensuite les agents spécialisés.
  • Accès aux sources : les agents consomment Dataverse TPG (tpg_*) et SharePoint (Idexios-Prime) via les actions/connecteurs; des sources personnalisées peuvent être arrimées si configurées.
  • Retour agentique : les résultats (KPI, écarts, recommandations, preuves) reviennent à Idexios, qui met à jour le contexte et prépare la sortie.
  • Sorties : conversation, Power Pages (Adaptive Cards/rapports), ou déclenchement de processus (création/MAJ d’enregistrements).

Les sections de rubriques ci-dessous détaillent, pour chaque intention, les entrées, traitements, colonnes d’Adaptive Cards et rapports attendus.

📊 Rubrique PORTEFEUILLE — Exemple complet (ATHENA-PORTF)

Scénario d'usage

Cette rubrique synthétise les informations clés (nombre de projets, budgets totaux, coûts engagés, capacité, bénéfices cibles, risques majeurs) par portefeuille. Un cas typique consiste à comparer plusieurs portefeuilles ou programmes et à identifier les projets qui nécessitent une décision ou une escalade.

Finalité métier

Vue portefeuille pour comité de direction / PCO : projets à risque, EVM (SPI/CPI), capacité, dépendances et décisions à trancher.

Drill-down (logique contextuelle)

Question PROJET → ancrage ProjectId ; question PORTEFEUILLE → ancrage PortfolioId ; question PROGRAMME → ancrage ProgramId. Les clés restent des GUID Dataverse, avec résolution possible via code et nom (disambiguation).

🧾 Sous-flux FinOps (Showback / Chargeback) — Portefeuille

Dans la rubrique Portefeuille, le volet financier est traité comme un sous-flux spécialisé : je consolide les coûts par centre de coûts et par hiérarchie PPM (Projet → Programme → Portefeuille), en appliquant les règles d’allocation normalisées via CostAllocationKey. Par défaut, j’analyse mois courant + mois suivant et je fais confirmer cette fenêtre à l’utilisateur avant d’exécuter les calculs.

Description du flux

Traitements (règles de calcul)

  • Normalisation : j’applique les règles de mapping pour produire une CostAllocationKey stable (dimensions → clés de référence).
  • ShowbackAmount : j’agrège les coûts par CostAllocationKey pour fournir une visibilité (sans refacturation).
  • ChargebackAmount : j’applique les formules de refacturation réelles (périmètre + règles + exceptions), puis j’agrège au niveau comptable attendu.
  • Agrégation temporelle : par défaut M0 + M1, avec option de bascule Semaine/Mois/Trimestre/Intervalle sur confirmation utilisateur.
  • Seuils d’alerte : je déclenche les alertes portefeuille sur VariancePct (ex. vert < 10%, jaune 10–20%, rouge > 20%).

Décisions d’architecture (justification)

  • Clés de forage : je garde projectId, portfolioId, programId en contexte pour garantir un drill-down déterministe.
  • Période par défaut M0+M1 : c’est le compromis “opérationnel” pour comité (projection courte) tout en restant confirmable.
  • RAG SPI/CPI : je normalise le rendu UI pour éviter que deux agents présentent des seuils différents.
  • Chemin critique : je mappe CriticalPathFlag sur tpg_projecttask.tpg_iscritical (testé), ce qui me permet un tri “exécution” sans interprétation.

Composantes du Système

Architecture détaillée des composantes d'Idexios : instructions système, sources de connaissances, comportement analytique et mécanismes d'orchestration.

Lecture du diagramme

Les composantes décrivent les blocs d'implémentation du toolbox agentique dans Copilot Studio. Idexios orchestre les rubriques, appelle des actions (connecteurs) et assemble les sorties selon trois formats : conversation, Power Pages (cartes/rapports) et intégration de processus (écritures Dataverse/SharePoint).

  • Report Factory : génération automatisée de documents et artefacts via Azure Function ou Logic App, alimentée par Dataverse et les gabarits Idexios-Prime.
  • Case Management : suivi des exceptions, anomalies et approbations via liste SharePoint (Idexios-Prime).
  • Observabilité : corrélation des appels (traceId) et journalisation des décisions/routages.
  • Sécurité : RBAC, DLP et audit appliqués aux connecteurs et aux ressources SharePoint/Dataverse.

Vue d'ensemble - Mission et Capacités

Idexios transforme les intentions stratégiques en actions coordonnées, servant de hub intelligent pour l'écosystème d'agents de gestion de projet Reddixia.

Description du processus

Le schéma représente un enchaînement type de bout en bout. Une requête déclenche la qualification de l’intention, la résolution du contexte (portefeuille/programme/projet) et de la période, puis le routage vers le Domain Pack pertinent. Les agents spécialisés exécutent les traitements (lecture/écriture via connecteurs), assemblent des résultats vérifiables et renvoient des sorties standardisées pour le pilotage (cartes, rapports, items de suivi).

Les décisions et exceptions à tracer (approbations, anomalies, écarts, corrections) sont matérialisées sous forme de cases dans Idexios-Prime, afin d’assurer la continuité opérationnelle et l’auditabilité.

Vue d'ensemble du modèle de données

Le schéma relationnel TPG_PPP&S structure les données de gestion de portefeuille, programmes et projets (PPP) dans Dataverse. L'information est organisée autour d'entités clés utilisées par Idexios pour le drill-down contextuel et les calculs de pilotage.

  • tpg_portfolio - Portefeuilles regroupant programmes et projets stratégiques
  • tpg_project - Projets avec budgets, échéanciers, bénéfices et drivers
  • tpg_projecttask - Tâches WBS avec dépendances, chemin critique (tpg_iscritical), et affectations
  • tpg_financials - Données financières par période pour calculs EVM (PV, EV, AC)
  • tpg_capacity - Capacité planifiée et timesheets réels pour contrôle d'effort
  • tpg_period - Périodes fiscales pour agrégation temporelle

Les clés primaires sont des GUID Dataverse, permettant le drill-down contextuel (ProjectId, PortfolioId, ProgramId) et la résolution par code/nom pour disambiguation.

FinanceOps Pack — Objectif et flux

Analyse financière et discipline FinOps (Finance & Opérations), détection d'anomalies, contrôle des variances et clôture de période.

Cadre de coordination de valeur (TBM / VMO / Lean Portfolio Management) : les agents financiers appliquent un raisonnement orienté valeur pour décider du niveau d’effort, prioriser les analyses et structurer la reddition de compte.

  • TBM : avant extraction/calcul intensif, justification du coût (temps/tokens/API) vs l’objectif métier; réduction des traitements non nécessaires.
  • VMO : priorisation des actions maximisant le ROI/KPI; les jalons sont évalués en valeur générée (précision, gain de temps, alignement), pas seulement en avancement.
  • LPM : itérations courtes, points de contrôle et “fail fast”; arrêt/réorientation si la valeur attendue n’est pas démontrée rapidement.
